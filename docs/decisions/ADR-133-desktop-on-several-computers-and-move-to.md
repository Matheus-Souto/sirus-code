# ADR-133: The desktop app on several computers, and "Move to"

**Status:** Accepted (2026-10-14).

## Context

The owner starts work on the Mac and wants to keep going from the phone after closing the laptop, with the desktop app, the web app and the phone pointed at a server on a VPS. Sirus already runs headless on a VPS (`sirus-host`, ADR-131) and one phone app talks to several computers (ADR-132), but the Mac app only ever talked to itself through Tauri's IPC, and a conversation that started on the Mac lived only there.

## Decision

### Computers in the desktop app

- **Same list, same pairing.** Settings → Connections gains a Computers group: this Mac (always, the `home` computer) and Add computer with the host's `https://….ts.net` address and the six-digit code from `sirus-host pair` (or another Mac's Connections). The desktop reuses `lib/environments.ts` (`readEnvironments`, `pairedEnvironment`, `upsertEnvironment`, the `sirus.environments` key) and pairs with `redeemPairingAt`, cross-origin from its own page. Computers can be used, renamed and forgotten (the token is dropped here; revoking stays on the host).
- **Where the token lives: the webview's local storage.** Considered: a Rust-side `computers.json` (`0600`) in the app data folder, or the Keychain. Local storage was chosen because the token is used by the webview anyway (the WebSocket to the host is opened there), it is stored per user in the app's own WebKit data, and — decisive — it never crosses the Mac's IPC: a Rust store would need a command that reads the tokens, and every command is reachable by paired phones through the Mac's own remote server unless it is kept in the `DENIED` list forever. The Keychain would add prompts and a dependency for no gain over the user-only WebKit store. The dev build (`http://localhost:1420`) has its own storage and its origin is not accepted by hosts; pairing is for the bundled app.
- **One active computer, the whole window on it.** On the desktop `client` now also sits on the `SwitchingTransport` (ADR-132), starting on a `LocalTransport`. Using another computer (`useComputers.activate`, `store/computers-store.ts`) snapshots this computer's data as a summary, switches the transport to that host's `RemoteTransport` and runs `bootstrap()`: transcript, composer, terminals, files, changes and review all run there. Commands and events that belong to this Mac's window stay on it whatever computer is active (`runsOnThisMac` / `eventFromThisMac` in `lib/computers.ts`): remote access, pickers, dictation, computer use, window snap, prompt links, chat background, notifications, the embedded browser and devices. Remote access settings always use `localClient`. The desktop opens on this Mac each time.
- **Other computers in the project switcher.** Each other computer (this Mac too, while a server is active) is watched through its own client for a trimmed summary (projects, recent conversations, archive and pin lists, `session-updated` and `settings-changed` kept live). The project switcher lists them below the active computer's projects under a small laptop or server marker with the computer's name, its projects and up to five recent conversations; choosing one switches computers first. An offline computer's last-known rows show dimmed with "<name> is offline". A quiet chip before the project title shows the computer in use once a second one is paired; its menu switches computers.
- **New projects choose a computer.** With several computers the New project dialog has a Computer control, defaulting to the last one chosen (`sirus.computers.lastTarget`); choosing another computer switches to it before creating, cloning or opening. On a server the parent folder defaults to `~/projects` and the Browse button is hidden (typed paths only). New sessions go to the computer of the project they are started in.
- **Capabilities.** The window follows `host_info.capabilities` of the active computer (`hostFeatures`): no Browser or Devices panels, no Computer use settings, no editor apps (open in editor), and the folder picker gives way to the New project dialog. Attachments come from the webview's file input and are uploaded (`paste_prompt_attachments`), as on the phone. Dictation stays the Mac's own.
- **CSP and origin.** `tauri.conf.json` allows `connect-src https://*.ts.net wss://*.ts.net` (and `img-src` for the dev build). `remote.rs` accepts the Tauri page's origin (`tauri://localhost`, `http(s)://tauri.localhost`, exact matches) like a tailnet page of ADR-132: open for `/api/pair` and `/api/health`, recorded on the device it pairs, and only then allowed on the API and socket, with the socket token bound to that origin. Device tokens stay mandatory everywhere. Any Tauri app shares that origin, so the protection is the code and the token, as for pages on the tailnet.

### "Move to <computer>"

- A conversation's menus (sidebar row, header tab, project switcher) offer "Move to <computer>" for each other paired computer, disabled while it does not answer. A confirmation explains what happens; it refuses a running conversation, side chats and projects without a GitHub `origin` (the other computer could not get the files) and says why.
- **Steps** (`useComputers.moveSession`): (1) the project's GitHub address on the source (`project_remote_url`); on the target `find_project_by_remote` matches it against each project's `origin`, else `clone_project` clones it into the target's projects folder. (2) `prepare_session_move` (confirmation required) snapshots the session's checkout — uncommitted and untracked files, through a private index on top of `HEAD` (`team::snapshot_commit`), so the person's files, branch and staging area are untouched — and pushes that commit to `origin` as `sirus/move-<first 8 of the session id>` (`git::push_commit_to_branch`: never forced, same network-helper refusal as push). It returns the branch, title, provider, model and the transcript as text (user and agent messages, finished, at most 2,000 messages, 256 KiB each, 8 MiB in total, the most recent kept). (3) `import_session` on the target fetches the branch, checks it out in a new isolated worktree tracking `origin/<branch>` (`worktree::create_from_origin_branch`, refused if the branch already exists there), creates the session with the same provider and model (the usual provider and model checks), copies the transcript as new messages and arms the handoff recap of ADR-028 (`arm_in_session_handoff`), so the first turn there carries "You are continuing an existing conversation…" with the recap; the setup script runs as for any new worktree. Requests are strictly validated (`deny_unknown_fields`, a `sirus/move-…` branch, the same size limits, no system rows or NUL bytes, a one-line computer name) and a failure after the worktree was made removes it. (4) `mark_session_moved` notes on the source where it went; both sessions carry `movedTo` / `movedFrom` (`{ computer, branch, at }`, `models.rs` ↔ `types.ts`) shown as one quiet line in the transcript ("Moved to sirus-vps on branch sirus/move-1a2b3c4d", with Open there). The window then switches to the target and opens the new conversation.
- All four commands are in `lib.rs`'s handler list, so the headless host gets them from the generated table (ADR-131).

## Consequences

- Closing the Mac no longer strands a conversation: move it to the server, then continue there from the phone or from the Mac app later.
- Native notifications come only for this Mac's conversations; a server's alerts reach the phone through web push (ADR-082). The commit made by a move is authored "Sirus Code" (the team snapshot's identity), not the person.
- The desktop's computer store (`computers-store.ts`) repeats the phone's watching logic (`environments-store.ts`) instead of sharing it, to keep the two surfaces independent while the phone's store was changing; they can be merged later.
- The phone's long-press menu does not offer "Move to" yet.
- Both computers need this version: the host for the CORS origin and the new commands, the Mac for the CSP.

## Addendum (2026-10-14): continuing while the computer is off

"Move to" needs the source computer to push the work. When the phone shows a conversation whose computer is out of reach, the waiting-messages banner offers "Continue on <computer>" for each other computer that answers (`useEnvironments.continueOn`). The phone sends what it has: the transcript it shows (`travellingMessages`, the same bounds as a move) and the project's GitHub address, noted per computer and project while that computer answered (`phone-continue.ts`, `sirus.projectRemotes`). The target finds or clones the project as in a move (without a noted address, a project there with the same name is used), and `import_session` with `fromOrigin` (the conversation's branch) fetches that branch from `origin`, or the default branch when it was never pushed, and starts a new `sirus/move-…` branch from it without tracking it (`worktree::create_from_origin_start`), so pushes never land on the base branch. The handoff recap starts with a note that changes only on the other computer (uncommitted or not pushed) are missing. Waiting messages move to the new conversation (`retargetQueued`) and go out there. The confirmation says all of this before it runs. The source conversation is not marked as moved, because its computer is off.

## Addendum (2026-10-14): one list, no computer picker

The owner chose this model over a window-wide computer picker. The header's computer chip is gone. The project switcher is one list across computers (`mergeComputerProjects`): another computer's project with the same name as one here joins that row, marked by the machine's icon ("Also on sirus-vps"), and its conversations list under this computer's, each with the icon; a project only on another computer gets its own row after this computer's. Choosing a row on another computer opens it there (the window still switches underneath, as before). A new conversation's landing tray has "Run on" before the workspace choice, listing the computers that have the project (by name; the others are disabled with a note), and a conversation on another computer than this Mac shows that computer as a quiet label tucked under the composer, as a locked "Run on". Settings → Connections still pairs, renames and switches computers.
