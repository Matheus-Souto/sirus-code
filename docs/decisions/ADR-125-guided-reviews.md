# ADR-125: Guided reviews

**Status:** Accepted (2026-10-13).

## Context

A large pull request, or a long agent turn, is hard to review file by file in diff order. The order that explains a change is usually different: the data shape first, then the code that implements it, then its callers. A guide answers this: a tour of stops, each pointing at the lines worth reading, written by a model. Sirus already has the pieces to host one (the Pull requests page, the Changes pane on the Mac and the phone, and the always-on agent tools of ADR-111 and ADR-123), but no place to keep such a tour or to walk it.

## Decision

- **Model.** A guide (`review_guides.rs`, mirrored in `client/types.ts`) has a target, a title, an optional Markdown summary, an optional `headSha`, and ordered steps. The target is a GitHub pull request (`repository`, `number`) or a session's uncommitted changes (`sessionId`). A step has a title, a Markdown body, an optional `attention` (the one call the reviewer should make there) and up to 8 anchors `{ path, side: new|old, start, end, caption? }`. There is one guide per target; writing again replaces it in place and bumps `revision`.
- **Agent tools.** `sirus_write_review_guide` (`pullRequest?` as `owner/repo#123` or a GitHub link, `title`, `summary?`, `headSha?`, `steps`) and `sirus_read_review_guide` (`pullRequest?` or `sessionId?`, default the caller). They are always on, like visuals (ADR-123), because they only store a guide and never change code; a planning caller may write one. Without `pullRequest` the guide is for the caller's own changes; an agent cannot write another session's guide. The tool description carries the writing rules (reading order, one call per step at most, anchors inside the hunks, mechanical changes grouped at the end).
- **Validation.** Titles are one line (≤120 characters, steps ≤160), bodies and the summary ≤4,000 characters, attention ≤400, captions ≤160; 1–24 steps; anchors use repository-relative paths (no absolute paths, `..`, backslashes or control characters; a leading `./` is dropped), lines from 1, at most 400 lines each, reversed ranges are swapped; `headSha` is 7–64 hex characters. A refused guide returns the reason so the agent can fix it.
- **Storage.** `AppData.review_guides` is stored one row per guide in a `review_guides` table (store migration 4), like projects and tasks, so a write touches one row. At most 40 guides; the least recently written go first, and a session's guide goes with the session. Older databases and JSON state load without the field. `load_state` leaves guides out; the UI reads one at a time with `review_guide_action` (`get`, `delete`) and reloads on `review-guides-changed` (`{ key }`).
- **Anchors are resolved, not trusted.** The UI finds an anchor's rows in the parsed diff by the line numbers on its side (`lib/review-guide.ts`); `a/` and `b/` prefixes are tolerated. An anchor outside the diff is shown as such (dashed chip, a note) instead of pointing at the wrong lines. A pull request guide whose `headSha` differs from the current head says it was written before the latest push.
- **UI.** `ReviewGuideTour` shows the title, a steps menu, a segmented progress bar (each segment jumps to its step), the stale note, the step (number, title, overview on the first step, attention, Markdown body, anchor chips) and Previous / Next; ← and → move while focus is in the tour, and the step content slides in the direction of travel (fades only with reduced motion). `DiffViewer` takes a `focus` (rows, key): the rows get an accent bar and tint over their addition/deletion color, are mounted even in a chunked diff, and scroll into the upper part of the diff's own scroller.
  - **Pull requests page:** a Guide tab beside Code. With a guide, the tour sits above the anchored file's diff; the ⋯ menu asks for a new guide or deletes it. Without one, "Ask an agent for a guide" opens a new session in the repository's project with a request naming the tool, the pull request and its head; as with Send to agent, nothing is sent until the person presses Send.
  - **Changes pane:** a signpost button beside Refresh. Without a guide it puts a request in the session's composer; with one it opens the compact tour above the file list, and each step opens the anchored file's diff (unstaged first, then staged). The phone's Review screen wraps the same pane, so the tour works there with no phone-specific code.

## Consequences

- An agent can hand the person a reading order for its own work or for any pull request, and the person walks it beside the real diff.
- Guides are only as good as the agent's line numbers; anchors that miss the diff are visible as misses rather than silently wrong.
- Left out: a background generation run with progress, server-side clamping of excerpts to hunks, per-line notes, suggested questions, review-comment collection from the tour, per-project guide instructions, and stacked-PR context. Guides of pull requests are kept on this Mac only.
